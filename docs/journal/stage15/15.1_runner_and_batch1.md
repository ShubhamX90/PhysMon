### J15.1-008 · 2026-11-13 · incident
kind: incident
**What happened [V]:** five generic workers started far earlier than `--test-only` predicted (444874 and 444875 on gpunode7 H200 from 2026-11-12T18:07; 444877-444879 on gpunode4 A100 from 2026-11-13T08:48). Every vLLM entry failed at engine start ("Cannot re-initialize CUDA in forked subprocess" → "Engine core initialization failed"); the HF parity run succeeded (80 records, 78 COMPLETE, job 444874, H200). Each failed entry was attempted once per worker; no vLLM record was written and no claim was left. Logs: `/scratch/pabitra/physmon/slurm_logs/4448{74,75,77,78,79}_*`.
**Cause [V]:** the runner called `torch.cuda.is_available()` in the parent before `vllm.LLM()`; that poisons a later fork without marking CUDA initialised, so vLLM 0.33 (`vllm/utils/system_utils.py` `_maybe_force_spawn`, which checks `torch.cuda.is_initialized()`) kept its default fork start method for the engine-core process.
**Why the checks missed it [V]:** every pre-flight ran on the login node, which has no GPU (`--check-only` skips all CUDA steps), and the pre-submission review checked vLLM's API, not its process model. No check had executed vLLM on a GPU. This was a gap in verification, stated plainly.
**Fixes [V]:** (1) the vLLM path never touches `torch.cuda` in the parent (GPU presence and name from `nvidia-smi`), with a regression test that fails if it does; (2) `VLLM_WORKER_MULTIPROC_METHOD=spawn` is hard-set before `LLM()` (confirmed in vLLM's `get_mp_context` and `launch_core_engines`; the runner is import-safe as `__mp_main__`, tested); (3) **canary gate**: four small canary runs (6 problems × 2 samples) mirror each real vLLM configuration exactly; a dependent run's queue holds `gate.json`, and the runner (in the run's own snapshot, so the already-queued workers enforce it too) exits in seconds unless every required canary has finished on a GPU with valid records (all shards done with matching checksums, no record errors, every record OK with tokens and finish reason stop/length, at least one COMPLETE). Tested, including on the real HF parity records (passes).
**Second independent review (GPU-only paths, read against the installed vLLM 0.33 source) [V]:** confirmed the cause and fix; found one wrong-data defect, fixed: an `abort`/`error`/`repetition` finish was recorded as an ordinary outcome → now an explicit RECORD_ERROR that keeps the text. Risks acted on: Triton needs a C compiler on the compute node (never exercised there; gpunode6 is known to lack a usable git) → the runner test-compiles with the node's gcc, else a shared conda toolchain on scratch, and refuses before loading the model if neither works; spawn hard-set rather than defaulted; vLLM engine settings recorded in every record (`backend_config`); the seed claim corrected (vLLM samples are per-request seeded but not batch-invariant: `seed_scope` "request_not_batch_invariant"). Verified fine from source: `LLM()` arguments, output order, `SamplingParams` validation, stop tokens equal the HF backend's for Qwen2.5, Qwen3 and Llama-3.1, KV-cache memory feasible for every spec on 80 GB and 141 GB cards.
**Re-registration [V]:** the five vLLM runs had no records, so they are re-pointed at the fixed commit (`register --replace`, which refuses any run with done or claimed shards) and gated on their canaries. The HF parity run is complete and untouched.
